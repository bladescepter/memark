# 个人 AI 记忆系统重构与构建方案

> 状态（2026-09-23）：P1 协议、P2 首批迁移和 P3 扩展主体已完成；v0.3.1 已完成写入安全加固，基线与当前主机注入已实现、待逐机实测；原计划三机实测后验收 P3。现确认共四台已知设备，第四台 Linux 笔记本是否运行 Pi 尚未核实，接入时再补测。Hindsight 已于 9 月 23 日在 pi-web 停用、memark 同期开始试运行；这不等于 Hindsight 容器/数据卷已停用或 P6 完成。P4 Jev Gate 和 P5/P6 尚未实施。
>
> 核心结论：**以 Markdown/Git 作为长期记忆唯一真相源，以 Jev 作为每轮对话后的低成本候选筛选器，以 Curator 流程（单一 Pi 扩展承载）负责提炼和归档，以用户批准作为正式写入闸门；Hindsight 进入只读迁移期，验证完成后退出。**

---

## 1. 背景与问题定义

当前使用的 Hindsight 记忆效果总体可用，但自动记忆持续摄入大量噪声，已经出现以下结构性问题：

1. 自动 retain 无法稳定区分长期有效事实、一次性任务状态、临时排错过程和助手推测。
2. 记忆库增长后，`memory_links`、实体、chunks、审计记录等派生数据同步膨胀。
3. 心智模型依赖定时生成和刷新，容易出现空内容、过期内容、标签遗漏以及摘要漂移。
4. 心智模型内容无法天然成为可靠事实源；它只是从候选记忆派生出的摘要。
5. 所有项目共用 Hindsight 服务，需要长期占用 VPS 内存和数据库资源。
6. 跨设备共享仍然绑定于 Hindsight API，不利于迁移和审计。

当前实例检查结果显示，Hindsight 与 PostgreSQL 合计占用约 1.2 GiB 常驻内存，数据库约 794 MB，系统已经使用 Swap；当前还存在 retain queue dead letter。现有心智模型中，`综合助手`曾出现只剩空标题的情况，`环境与资产明细`也存在版本信息滞后于实际环境的问题。

因此，本次目标不是简单清库，而是改变记忆系统的控制边界：

> **自动系统只负责发现候选，不再拥有未经确认的长期写入权。**

---

## 2. 目标与非目标

### 2.1 目标

- 控制长期记忆膨胀，显著降低噪声比例。
- 让每条正式记忆都可读、可审计、可修改、可回滚。
- 让 pi 会话在当前已知四台设备（工作 PC、家庭 PC、Linux 笔记本、VPS）上运行时共享同一套记忆，同时准确区分当前执行主机与访问它的客户端。
- 释放 Hindsight 和 PostgreSQL 在 VPS 上的长期资源占用。
- 将个人偏好、项目决策、工作方法和临时交接状态分开管理。
- 对每轮对话进行低成本的自动候选筛选，但不自动写入正式记忆。
- 保留 Hindsight 现有有用记忆，经过人工审核后迁移，而不是把数据库噪声整体搬家。

### 2.2 非目标

- 不重新搭建一个新的常驻 RAG 服务。
- 不把完整会话日志永久转换为长期记忆。
- 不让 Jev 生成记忆正文；Jev 是决策模型，不是文本生成模型。
- 不让心智模型代替项目文件、代码、测试结果、运行时状态或用户最新明确决定。
- 不追求所有历史对话都可检索；只保留会影响未来工作的内容。
- 不把密码、Token、私钥、Cookie 或完整 `.env` 内容放入记忆仓库。

## 3. 最终架构

```text
┌─────────────────────────────────────────────────────────┐
│                 Pi（可能运行于四台设备）                   │
│      工作 PC · 家庭 PC · Linux 笔记本 · VPS 上的会话        │
└──────────────┬──────────────────────────┬───────────────┘
               │ recall                   │ agent_settled
               ▼                          ▼
      ┌─────────────────┐       ┌──────────────────────┐
      │ Recall 工具      │       │ Pi Memory Gate       │
      │ 按需读取记忆     │       │ 每轮结束后候选筛选     │
      └────────┬────────┘       └──────────┬───────────┘
               │                           │
               │                           ▼
               │                  本地硬规则与脱敏
               │                           │
               │                           ▼
               │                         Jev
               │                结构化判断、概率、置信度
               │                           │
               │                           ▼
               │                    pending 候选区
               │                           │
               │                           ▼
               │                    Curator 工具
               │               提炼、分类、去重、生成 diff
               │                           │
               │                           ▼
               └───────────────► 用户批准后写入 ◄──────────────┐
                                      │                       │
                                      ▼                       │
                         Markdown + Git 长期记忆库            │
                                      │                       │
                                      ▼                       │
                           私有 Git remote / VPS              │
                                                              │
                         Hindsight：只读迁移源，最终退出 ──────┘
```

### 3.1 组件职责

| 组件 | 职责 | 是否有正式写入权 |
|---|---|---:|
| Pi Memory Gate | 每轮对话结束后判断是否产生记忆候选 | 否 |
| Jev | 进行快速、结构化、带概率的分类和评分 | 否 |
| 扩展 recall 工具 | 从索引和相关文件中读取上下文 | 否 |
| 扩展 curator 工具 | 把候选提炼为规范记忆，识别重复和冲突 | 仅生成草案 |
| 用户 | 确认、修改或拒绝候选记忆 | 是 |
| Git | 记录版本、审计、回滚和跨设备同步 | 不判断内容 |
| Hindsight | 迁移期查询旧记忆，之后停用 | 迁移期不自动 retain |

### 3.2 已知设备与身份边界

以下设备名只用于人工清点，**不注入 Agent**；Agent 只需知道本机角色和实时 OS。角色由用户在每台机器首次交互使用时设置，不靠设备名或 OS 猜测。四台是否都已挂载 Pi 尚未核实。Windows/Omarchy 设备名来自已审核的个人记忆，系统版本尚未到各机核验；VPS 的系统于 2026-09-23 在当前运行环境实测。memark 不读取或校验 hostname。

| 设备（人工清单） | 建议设置的本机角色 | 操作系统 | 已知程度 |
|---|---|---|---|
| 腾讯云 VPS | `VPS`（pi-web 的 Pi 进程运行处） | Ubuntu（当前实测 24.04.4 LTS） | 角色待首次使用时设置 |
| `Blade-Latitude` | `工作电脑` | Windows（版本未核实） | 记忆中的设备名；待本机设置角色 |
| `Blade-ThinkBook16P` | `家庭电脑` | Windows（版本未核实） | 记忆中的设备名；待本机设置角色 |
| `blade-thinkpad` | `Linux 笔记本` | Linux / Omarchy（版本未核实） | 记忆中的设备名；待本机设置角色 |

**身份边界**：`pi.xiyuan.wiki` 的访问者可以坐在任意客户端，但 pi-web 的 Pi 进程和本地工具执行在 VPS；不能把浏览器所在设备当成 Agent 当前主机。在 PC 终端本地运行 Pi 时，Agent 当前主机才是该 PC。若工具通过 SSH、容器或远程执行器运行，应单独核对命令的实际执行目标，而不是用 Pi 进程主机代替目标主机。设备名/OS 记忆只描述拥有的设备，不证明当前所在机器；OS 可能改变，以运行时证据为准。

## 4. 记忆分层与真相优先级

### 4.1 五层个人记忆

借鉴《一文搞懂个人 AI 记忆系统构建全流程》的五层设计：

```text
identity      我是谁
principles    我的原则、判断底线和长期工作纪律
preferences   我希望 AI 怎样与我协作
context       当前阶段、关系、环境和正在进行的事项
knowledge     可复用的技能、经验和学习成果
```

建议目录最多两级：二级目录下直接放文件，禁止无限嵌套。目录深度固定，迫使维护者在分类和内容之间作出明确判断。

记忆仓库结构（个人区 + 项目区）：

```text
memory-repository/
├── README.md                         # 路由和写入规则，唯一分类权威
├── INDEX.md                          # 自动生成的总索引（仅个人区）
├── identity/
│   ├── README.md
│   └── *.md
├── principles/
│   ├── README.md
│   └── *.md
├── preferences/
│   ├── README.md
│   └── *.md
├── context/
│   ├── README.md
│   ├── relationships/
│   │   ├── README.md
│   │   └── *.md
│   └── current/
│       ├── README.md
│       └── *.md
├── knowledge/
│   ├── README.md
│   ├── skills/
│   │   ├── README.md
│   │   └── *.md
│   ├── experiences/
│   │   ├── README.md
│   │   └── *.md
│   └── learnings/
│       ├── README.md
│       └── *.md
├── projects/                         # 项目区：单项目有效记忆，一项目一目录
│   └── <项目名>/
│       ├── README.md                 # 该项目路由
│       ├── INDEX.md                  # 自动生成，仅该项目
│       ├── decisions/                # 架构决策及理由（Decision）
│       ├── topics/                   # 已验证的项目知识（Topic）
│       ├── incidents/                # 可复用的事故教训（Incident）
│       └── handoffs/                 # 未完成工作的交接（Handoff，须设 expires）
├── pending/                          # 待审核候选，不是正式记忆
├── archive/                          # 已归档或被替代的记忆
├── audit/                            # 维护报告和统计，不注入 Agent
└── scripts/                          # 索引、校验、脱敏和同步脚本
```

`pending/`、`archive/`、`audit/` 是系统管理区，不参与普通 recall；正式记忆仍遵守最多两级内容目录的约束。

### 4.2 项目记忆与个人记忆：分区不分库

个人记忆与项目记忆在概念上严格分离，在物理上存放在同一个记忆仓库，分两个区：

- **个人区**：五层目录（identity / principles / preferences / context / knowledge），准入标准为「跨项目有效」。
- **项目区**：`projects/<项目名>/`，准入标准放宽为「单项目有效即可」；每项目一个目录，含自己的 README 路由和自动生成的 INDEX.md，类目为 `decisions/`（Decision，架构决策及理由）、`topics/`（Topic，已验证知识）、`incidents/`（Incident，事故教训）、`handoffs/`（Handoff，工作交接，须设 `expires`）；`scope` 必须为 `project`。

单仓双区的理由：

- 非 git 项目（无远端仓库）也能有项目记忆；
- 三机只同步一条链路，项目记忆在任何机器上完整可用；
- 协议、校验脚本、审计历史集中一处维护，不必在每个项目里复制；
- 跨项目检索（「所有项目中关于 X 的经验」）只有单一索引才做得到；
- Hindsight 项目级心智模型有确定的迁移去处。

代价与对策：

- **失去与代码共版本化**（项目记忆的 commit 不随项目仓库走）：接受。项目记忆多数是工作约定与教训，随工作流而非代码 commit 演进；记忆仓库的 Git 历史仍提供完整审计。
- **AGENTS.md 职责边界**（防止两处漂移）：项目仓库的 `AGENTS.md` 只保留「每轮必须自动注入的硬规则」（少数、稳定、精炼）；背景、历史决策、事故教训、交接存项目区、按需 recall。同一内容不两处存放；引用方向只能从项目 `AGENTS.md` 指向记忆仓库，不反向。

分类原则：

- 用户跨项目偏好、长期工作纪律 → 个人区五层。
- 某项目的架构、部署、接口、验证方式、教训 → 项目区 `projects/<项目名>/`。
- 每轮必须遵守的项目硬规则 → 项目仓库 `AGENTS.md`；记忆区只存背景和依据，不复制规则正文。
- 某次会话做到哪里、下一步是什么 → 项目区 `handoffs/`，默认过期。
- 当前版本、容器状态、内存、路径、端口 → 权威资产文件或实时检查，不作为稳定记忆。
- 项目文件和运行时证据与记忆冲突时，以当前证据为准。

### 4.3 真相优先级

```text
当前代码、项目文件、测试、API、数据库和运行时证据
    > 用户最新明确确认的内容
    > Git 中已审核的长期记忆
    > Curator 生成的派生摘要
    > Jev 判断结果
    > 未审核候选和助手推测
```

记忆中的高权重只表示“更优先提示”，不表示它可以覆盖当前事实。

## 5. 文件格式与治理字段

每个正式记忆以一个独立 Markdown 文件保存。目录决定大类，frontmatter 负责检索和治理。

### 5.1 必填字段

```yaml
---
type: Preference
title: 清晰直接的命名偏好
description: 命名和表达应直接易懂，避免不必要的抽象黑话
status: active
privacy: internal
tags: [沟通, 表达]
timestamp: 2026-09-20
---
```

七个核心字段：

- `type`：Identity / Principle / Preference / Context / Skill / Experience / Learning。
- `title`：一句话标题，进入 `INDEX.md`。
- `description`：说明内容是什么、何时调用。
- `status`：`active` 或 `archived`；被替代的内容标记为 `superseded`。
- `privacy`：`internal` 或 `public`。
- `tags`：跨目录主题标签。
- `timestamp`：内容沉淀或确认日期，不等同于文件创建日期。

### 5.2 建议的治理字段

```yaml
scope: user                  # user / project / workflow / context
source: user-confirmed       # user-explicit / user-confirmed / verified-file / runtime-verified
expires: null                # context/handoff 可设置日期
supersedes: null             # 被替代的记忆文件或 ID
reviewed: true
```

治理要求：

- 没有依据的条目不进入正式记忆。
- 不确定内容写入 `pending`，不得写成当前结论。
- 内容发生实质变化时更新原文件或明确标记 `supersedes`，不重复新建同义文件。
- 旧结论不直接删除，先归档并保留 Git 历史。
- 不把权威文件正文复制进个人记忆，只保存“应如何使用权威文件”的工作法。

### 5.3 总索引

`INDEX.md` 是地图，不是第二份正文。每行至少包含：

```text
- [P] 清晰直接的命名偏好 — 命名和表达应直接易懂 — preferences/命名与表达.md
```

索引应由脚本根据 frontmatter 自动生成，避免正文和索引不一致。Agent 的读取顺序为：

```text
README.md 路由规则
    → INDEX.md 筛选候选
    → 相关记忆正文
    → 必要时读取项目文件和实时证据
```

## 6. Recall 读取方案

### 6.1 启动基线

通过 `before_agent_start` 每轮向**当轮系统提示**追加极少量上下文（已实现，待逐机实测；不持久化到会话或记忆仓库）：

- 必要的身份信息、核心安全与协作原则、少量长期偏好（只取本地 `INDEX.md` 中已审核、active、未过期的个人区 identity/principles/preferences 条目，读取其标题与描述；不注入项目记忆）；
- **当前 Pi 进程运行主机**的短标记：本机声明的角色和实时检查得到的 OS；设备 ID、hostname 和工作目录不由 memark 重复注入（Pi 本身已有工作目录上下文）。

新机器首次**交互**调用 `before_agent_start` 时提示用户设置当前 Pi 进程运行机器的角色（取 §3.2 的建议名称，如 `VPS`、`工作电脑`），保存于本机 Pi 配置目录的 `memark/host-role.json`，而非共享 `memory` 仓库。`/memory host` 可查看，`/memory host set <角色>` 可修改。扩展不读取、校验 hostname，也不使用设备 ID 或角色环境变量。无 UI、取消或角色无效时只提示“角色未确认”与实测 OS；本会话不重复弹窗，新会话可重试。绝不从 Windows/Linux 系统或共享设备清单猜工作/家庭/VPS；Pi 进程主机与 SSH/容器等远程命令实际执行目标须分别核验。

基线只读本地快照，不在启动或每轮联网；需手动 `/memory sync` 或按需首次 recall 更新本地快照。对注入文本施加 480 Unicode 字符 / 1100 UTF-8 字节的保守上限，目标为总计 ≤600 tokens；**具体 token 数因模型分词器而异，逐机测试须验证**。不把完整设备资产表或整个记忆库塞进提示词。按轮注入是为了在长会话和上下文压缩后仍可分辨本机；本机制不产生候选，也不写入记忆。

### 6.2 任务相关读取

根据用户任务和项目上下文进行按需 recall：

1. 读取 `README.md` 的调用判据。
2. 扫描 `INDEX.md` 的标题、描述和标签。
3. 使用文件名、标签和全文搜索筛选候选。
4. 只读取与当前任务相关的正文。
5. 如内容可变，优先回到项目文件或实时环境核验。

Recall 范围按区控制：

- 默认范围 = 个人区根 `INDEX.md` + 当前项目的 `projects/<项目名>/INDEX.md`（项目名由当前工作目录、其父目录或环境变量确定）；
- 只有用户明确要求时才跨项目检索全部项目区索引；
- 项目区记忆不注入全局基线；
- 不在会话启动时联网；每个会话第一次实际 recall 时才用短超时执行一次 `pull --ff-only`，失败则提示并使用本地快照，同一会话不重复拉取。

初版不引入 embedding 或向量数据库，优先使用确定性的目录、索引、标签和全文搜索。只有当实际评测证明漏召回明显，再增加可重建的 SQLite FTS 或向量索引；索引永远是派生物，Markdown 和 Git 才是源数据。

### 6.3 Recall 失败策略

- 找不到相关记忆：正常继续，不猜测、不生成补充事实。
- 记忆与当前证据冲突：报告冲突，以当前证据为准。
- 记忆已过期：不自动更新，进入维护候选。
- 读取服务或 Git remote 不可用：使用本地最近一次快照，不阻塞当前工作。

## 7. Jev 记忆门卫

### 7.1 Jev 的定位

Jev 是 TypeSafe AI 的 System One 决策模型，输入 `state` 和类型化问题，输出结构化值、概率和置信度，不生成自由文本。它适合分类、评分、路由和工作流分支，不适合生成记忆正文。

官方资料所述特点：

- 通过 `Choice`、`Score`、`Noul` 等原子问题输出结构化结果。
- 多个问题可以在一次请求中并行评估。
- 官方公布端到端延迟约 70–500ms，具体取决于请求和网络环境。
- 官方价格页面列出的输入价格约为 `$0.042 / MTok`，实际价格、限流和服务条款应以当前控制台为准。
- 当前仍属于早期产品，尚没有针对中文长期记忆筛选的公开评测。

### 7.2 触发时机

Pi 中不使用 `turn_end` 作为唯一触发点，因为一次用户请求可能包含多个内部 turn，工具调用过程中会重复触发。

推荐使用：

```typescript
pi.on("agent_settled", async (_event, ctx) => {
  // 此时本轮请求、工具调用、重试和压缩流程均已结束
  // 提取最近用户消息与最终结果，执行候选筛选
});
```

`agent_settled` 才代表本轮 Agent 运行真正结束。筛选任务必须异步、可取消、可失败降级，不能影响正常对话。

### 7.3 发送给 Jev 的状态

只发送最小必要上下文：

- 最近一条用户消息；
- 最终助手结论；
- 必要的工具结果摘要；
- 当前项目标识；
- 与候选判断相关的少量现有记忆摘要。

不发送完整历史会话，避免输入量随会话长度累积，也减少隐私暴露。

在发送前必须：

1. 执行本地 secret scan。
2. 发现 Token、密码、私钥、Cookie、完整环境变量时，直接拒绝进入记忆流程。
3. 对普通敏感信息按隐私策略脱敏或标记为 `internal`。
4. 不把完整原始候选写入日志。

### 7.4 本地硬规则先于 Jev

下列内容无需调用 Jev，直接丢弃或拒绝：

- 纯工具输出、日志、临时命令结果；
- 一次性进度、临时文件路径和短期排错步骤；
- 密码、API key、Token、私钥、Cookie 和完整 `.env`；
- 助手无证据的推测；
- 已明确过期且没有复用价值的内容。

以下情况直接进入高优先级候选：

- 用户明确说“记住”“以后都这样”“这是长期规则”；
- 用户明确确认某个项目决策、边界或工作纪律；
- 用户纠正了助手，并要求以后遵守；
- 已验证的项目架构、接口约束或事故教训。

### 7.5 Jev 并行问题

不要只问一个宽泛的“是否应该 retain”，而应拆为相互独立的判断：

| 字段 | 判断内容 | 建议类型 |
|---|---|---|
| `durable` | 未来多个会话仍可能有效吗 | Noul |
| `future_utility` | 对未来任务有明显复用价值吗 | Score/Noul |
| `user_grounded` | 是否来自用户明确表达或可验证事实 | Noul |
| `ephemeral` | 是否只是一次性任务、进度或排错过程 | Noul |
| `sensitive` | 是否包含不应保存或同步的敏感信息 | Noul |
| `explicit_request` | 用户是否明确要求保存 | Noul |
| `scope` | user / project / workflow / context / none | Choice |
| `candidate_action` | new / duplicate / update / conflict / discard | Choice |

Jev 只输出判断结果，不输出正文。候选正文由 Curator LLM 或用户从原始上下文中提炼。

### 7.6 初始决策规则

初始阶段采用保守规则，不让概率直接变成自动写入：

```text
如果本地 secret scan 命中：拒绝，不进入外部模型判断

如果 explicit_request 高且未发现敏感内容：进入 pending 或直接生成待确认草案

否则仅当：
  durable        >= 0.80
  future_utility >= 0.70
  user_grounded  >= 0.80
  ephemeral      <= 0.20
  sensitive      <= 0.05
才进入 pending

其他情况：丢弃候选，只记录统计，不保存原文
```

这些阈值是初始值，不是理论保证，必须用真实中文会话标注集校准。

### 7.7 Jev 不能做的事

- 不能证明一条事实是真的。
- 不能生成高质量记忆正文。
- 不能独立判断用户最新意图是否改变了旧原则。
- 不能绕过用户批准直接写入长期记忆。
- 不能替代项目代码、文档和运行时检查。
- 不能保证“语义上永不误判”；类型安全只保证输出符合预定义结构。

## 8. Curator 与正式写入流程

### 8.1 Curator 的职责

Curator（由单一 Pi 扩展的 curator 工具承载流程）负责：

- 读取 `README.md` 路由权威；
- 查看 Jev 通过的候选；
- 从候选上下文中提炼最小、可执行的记忆；
- 选择正确层级和目录；
- 查找重复记忆；
- 判断是新建、更新、合并、冲突还是丢弃；
- 生成 Markdown 草案和 diff；
- 同步 `INDEX.md`；
- 提交 Git，但必须在用户批准后进行。

### 8.2 正式流程

```text
一轮 Agent 运行结束
    ↓
本地硬规则过滤与脱敏
    ↓
Jev 结构化判断
    ↓
写入 pending/ 候选区
    ↓
检索已有记忆，判断重复和冲突
    ↓
在临时副本生成草案、索引并完成 schema/secret/重复/链接检查
    ↓
展示完整修改预览，由用户批准、修改或拒绝
    ↓
再次确认远端未变化
    ↓
写入正式目录并精确暂存本次计划内文件
    ↓
一个记忆条目一个 Git commit
```

用户确认前不得把草案写入正式目录或标记为 `reviewed: true`。失败回滚只能恢复本次计划涉及的文件，禁止使用会清除其他未提交修改的全仓恢复命令。

### 8.3 用户批准策略

分三种情况：

1. **用户明确要求记住，且内容边界清晰、没有敏感信息**：可以直接形成正式草案，但仍执行 secret scan、去重和 diff 检查；必要时只确认分类和措辞。
2. **Jev 自动发现的候选**：必须进入 `pending/`，由用户批准后写入。
3. **存在冲突、不确定或高隐私内容**：不得自动写入，必须人工确认。

正式写入不采用“每天定时自动 consolidate”的方式。维护可以定期提醒，但写入权始终受控。

### 8.4 维护命令建议

```text
/memory status                 查看仓库、索引、候选和同步状态
/memory recall <query>         按任务检索相关记忆
/memory review                 审核 pending 候选
/memory approve <id>           批准候选
/memory reject <id>            拒绝候选并记录原因
/memory maintain               去重、检查过期、重建索引
/memory forget <id>            归档或删除一条记忆
/memory sync                   pull --ff-only、检查和 push
```

## 9. Git 与多设备共享

### 9.1 推荐模式

```text
每台机器本地 clone 私有记忆仓库
        ↓
本地 recall，只读
        ↓
单一 Curator 写入
        ↓
commit + push 到私有 Git remote
        ↓
其他机器 pull --ff-only
```

扩展仓库按普通软件仓库管理（正常分支、合并、回滚），无单写者限制。

VPS 可以只提供私有 bare Git remote，不再运行 Hindsight 或新的记忆数据库。也可以使用私有 Git 托管服务，但必须确认隐私和备份策略。

### 9.2 并发规则

Git 不是并发数据库，不能让多台机器的 pi 会话同时写。规则如下：

- 任何写入前先 `git pull --ff-only`。
- 非 fast-forward 时停止自动写入，提示人工处理。
- 一个记忆条目一个文件，减少冲突面。
- `INDEX.md` 由脚本生成，不手工并发修改。
- 同一时刻只允许一个 Curator 写入。
- Recall 过程永远只读。
- 共享的只有经过审核的 Markdown 层；pi 会话文件、队列等本地状态不进仓库。
- Git 冲突解决后必须重新检查重复、冲突和索引，而不是只接受某一侧文件。

### 9.3 安全边界

- 记忆仓库必须是私有仓库。
- `.env`、密钥、证书、私钥和会话原始日志加入 `.gitignore`。
- 每次提交前执行 secret scan。
- 共享到 VPS 或第三方 Git 前，先检查 `privacy: internal` 文件。
- Git 历史不可轻易“忘记”，因此敏感内容不能先提交再删除。
- 记忆只保存事实、规则和方法，不保存完整对话原文。

## 10. Hindsight 迁移方案

### 10.1 迁移原则

Hindsight 不直接作为新系统的长期后端，而是作为只读迁移源。现有心智模型和事实都是候选材料，不是自动可信的最终内容。

### 10.2 阶段 A：止血和备份

1. 对 Hindsight PostgreSQL 做完整备份。
2. 备份配置、Docker Compose、镜像版本和当前心智模型配置。
3. 检查并处理 retain queue dead letter。
4. 关闭自动 retain。
5. 暂停心智模型的自动刷新和自动注入，避免迁移期间继续产生漂移。
6. 保留 Hindsight 查询能力，但不再向其中自动写入。

清空前必须完成备份和恢复验证。不得先删除原 bank 再尝试恢复。

### 10.3 阶段 B：人工提炼

迁移顺序：

1. 用户偏好和长期工作纪律；
2. 已确认的跨项目原则；
3. 各项目的架构决策、边界和已验证经验；
4. 可复用工作方法；
5. 当前 context 中仍有明确后续价值的事项。

以下内容默认不迁移：

- 一次性操作；
- 临时故障排查过程；
- 过期版本号、IP、端口、容器和内存数字；
- 完整资产表；
- 重复观察；
- 助手推测；
- 未经用户确认的偏好；
- 与当前项目无关的其他项目细节；
- 可能包含敏感信息的原始内容。

当前已有的 `用户偏好`、`综合助手`、`环境与资产明细` 等心智模型只能作为提炼入口。其中 `综合助手` 的空内容和 `环境与资产明细` 的过期字段不能直接迁移。

### 10.4 阶段 C：并行验证

新系统与 Hindsight 只读查询并行运行 2–4 周，使用真实任务比较：

- 有用记忆命中率；
- 错误或过期记忆率；
- 重复记忆率；
- 每轮候选数量；
- 每周人工维护时间；
- 启动注入 token 数；
- 跨设备同步冲突数；
- 敏感信息拦截率。

### 10.5 阶段 D：退出 Hindsight

新系统达到验收指标后：

1. 先停止 Hindsight 容器，不立即删除数据库卷。
2. 保留 SQL 备份、配置备份和最后只读快照。
3. 观察一段时间，确认新系统可独立工作。
4. 再删除 Hindsight 容器、镜像、模型缓存和数据库卷，释放内存和磁盘。
5. 归档 Hindsight 迁移报告，记录最终停用日期和恢复方式。

## 11. Pi 实现方案

### 11.1 单一扩展设计

Pi 实现整合为一个扩展，不再单独维护两个 Skill。理由：

- 门卫必须由扩展实现（`agent_settled` 事件只存在于扩展中），TS 模块反正要写；
- recall 做成扩展工具后，一次调用即可在内部完成索引检索并返回拼装结果，省去 Agent 手动逐层读 README → INDEX → 正文的多轮工具调用；
- curator 的路由权威本来就是仓库 `README.md`，独立 Skill 会形成两份重复指令；扩展工具只负责强制流程（schema 校验、secret scan、去重、diff、git commit），提炼判断仍由模型依据 README 完成；
- 安装面从「两个 Skill + 一个扩展」缩减为「一个扩展 + 一个记忆仓库」。

扩展与记忆分为两个独立仓库：记忆是只增数据和审计日志，扩展是安装一次的软件，生命周期、隐私边界和分发方式都不同，不混在一个 Git 历史里：

```text
memory/                          # 记忆仓库：私有，跨设备 git 同步
├── README.md                    # 路由权威
├── INDEX.md                     # 自动生成的总索引（仅个人区）
├── identity/ principles/ preferences/ context/ knowledge/   # 个人区：跨项目有效
├── projects/<项目名>/            # 项目区：decisions/topics/incidents/handoffs
├── pending/ archive/ audit/
└── scripts/                     # 索引、校验、脱敏（校验规则属于记忆格式契约，随数据走）

memark/                          # 扩展仓库：纯代码，可公开（memory + markdown）
├── package.json                 # pi 清单：pi.extensions
└── index.ts                     # 零依赖；Jev 用原生 fetch 调用
```

- 扩展安装：`pi install git:<扩展仓库>` 或 symlink 到 `~/.pi/agent/extensions/`；
- 路径配置：扩展通过环境变量（如 `MEMORY_REPO`）定位记忆仓库，默认 `~/DEV/memory`；
- 分工：记忆仓库自描述（协议 + 校验脚本，无扩展也能用 `scripts/` 自检），扩展仓库只承载 pi 集成逻辑。

扩展内部组件：

| 组件 | 形式 | 职责 |
|---|---|---|
| Gate | `on("agent_settled")` | 本地硬规则、脱敏、Jev 判断、pending 入队 |
| recall 工具 | `registerTool`，常驻 | 内部检索 INDEX 与正文，一次调用返回结果 |
| curator 工具 | `registerTool` | 校验草案、去重、secret scan；提交前经 `ctx.ui.confirm` 批准 |
| `/memory` 命令族 | `registerCommand` | status / review / approve / reject / maintain / sync / forget |
| 基线与主机注入（已实现，待逐机实测） | `on("before_agent_start")` | 首次交互由用户设置角色到本机配置；每轮只读本地摘要并注入本机角色与实时 OS；不使用 hostname/设备 ID；未知则标未知 |

单一扩展的故障面更大，因此所有事件处理必须 try/catch：Gate 失败静默跳过（fail-open），recall 失败提示后由 Agent 直接用 `read`/`grep` 读仓库降级——仓库本身是纯 Markdown，天然可降级。无 UI 模式（print/json）下 `ctx.ui.confirm` 不可用，curator 工具自动降级为只写入 pending，不做提交。

### 11.2 降级路径（仅 pi）

本方案暂不考虑其他 Agent，pi 是唯一入口，包内不附带技能。扩展不可用时（禁用、加载失败或主动停用）：

- 在各机全局指令（如 `~/.pi/agent/AGENTS.md`）保留一行说明：长期记忆位于本地 clone 的记忆仓库，按其 `README.md` 协议用 `read`/`grep` 直接读取；
- 仓库是纯 Markdown，无需扩展即可读取和检索；
- 写入退化为完全手动：编辑文件后运行 `scripts/` 校验再提交 Git；
- 未来若确需引入其他 Agent，在同一包内补标准 Agent Skills 格式的薄技能即可，协议层无需改动。

### 11.3 Gate 状态持久化

Jev 判断结果不应直接塞回模型上下文。可以通过 Pi 的 `appendEntry()` 保存以下元数据：

```json
{
  "customType": "memark-gate-result",
  "data": {
    "candidateId": "...",
    "decision": "pending",
    "confidence": 0.86,
    "scope": "project",
    "createdAt": "..."
  }
}
```

这类记录用于恢复、统计和审计，不参与普通模型上下文。

### 11.4 异常与降级

- Jev 超时或不可用：不阻塞对话，直接不产生自动候选；用户仍可手动 `/memory remember`。
- Git remote 不可用：写入本地 pending，等待后续同步。
- Curator 失败：保留原候选，不覆盖旧记忆。
- 索引生成失败：禁止提交正式记忆，提示修复。
- secret scan 失败：禁止发送到 Jev，也禁止提交 Git。
- 扩展加载失败：pi 仅记录日志并继续运行，此时自动门卫和 recall 工具均不可用，记忆读取退化为直接读仓库文件，不影响正常对话。

## 12. 评测与验收

### 12.1 标注集

从历史会话中抽取约 200–500 轮，人工标注：

- 应长期记忆；
- 不应记忆；
- 应更新已有记忆；
- 应归项目记忆；
- 应归 handoff；
- 敏感、不得发送或保存。

标注集不得把完整敏感内容上传第三方服务。必要时先脱敏或只在本地使用。

### 12.2 指标

初始验收目标：

| 指标 | 目标 |
|---|---:|
| 重要记忆漏检率 | ≤ 5% |
| 自动候选有效率 | ≥ 80% |
| 未经批准的正式写入 | 0 |
| 敏感信息进入正式记忆 | 0 |
| 重复候选比例 | ≤ 10% |
| 启动基线注入 | ≤ 600 tokens |
| Jev/API 故障阻塞正常对话 | 0 次 |
| 记忆冲突被静默覆盖 | 0 次 |
| 单周人工维护时间 | 可接受并持续下降 |

“候选有效率”可以偏高，“重要记忆漏检率”必须优先控制。初期宁可把少量候选送入 pending，也不要追求极端低候选量而漏掉长期约束。

### 12.3 验收条件

满足以下条件后才能完成 Hindsight 的全面退出（pi-web 已停用其记忆集成，不等于容器/数据卷已停）：

- 已完成精选记忆迁移并由用户审核；
- 连续 2–4 周运行无未授权写入；
- 敏感信息拦截通过；
- 原计划三台设备（工作 PC、家庭 PC、VPS）各完成一次跨设备读取与同步；Linux 笔记本接入 Pi 时另行验证；
- 主机注入上线后，从不同 PC 浏览器访问 pi-web 仍识别为 VPS，本地终端识别为对应设备，未知设备不被错误归类；
- Git 冲突和断网恢复流程验证通过；
- Jev 不可用时手动流程仍可用；
- 通过真实任务测试，Recall 质量不低于当前可接受水平；
- Hindsight 备份和回滚材料仍可用。

## 13. 实施阶段

### P0：立即止血

- 备份 Hindsight 数据库和配置。
- 关闭自动 retain。
- 暂停心智模型自动刷新和自动注入。
- 不清库，不删除数据。

### P1：建立 Markdown 协议

- 创建两个私有仓库：`memory`（数据、协议、scripts）和 `memark`（扩展代码）。
- 编写根 `README.md`、五层目录 README 和 frontmatter 规范。
- 实现 `INDEX.md` 生成和 schema/secret 校验。
- 确定 VPS bare remote 或私有 Git 服务。

### P2：迁移精选记忆

- 读取现有心智模型和高价值事实。
- 按个人、项目、workflow、context 分类。
- 删除重复、过期、一次性和无依据条目。
- 由用户审核首批正式记忆。

### P3：实现 memark 单一扩展

- [x] 完成索引匹配、正文补充检索、当前项目隔离和显式跨项目读取。
- [x] 完成候选审核、修改预览、批准、拒绝、归档和回滚。
- [x] 完成安全路径、精确暂存/回滚、本机写入锁、离线 pending 降级和按需首次同步。
- [ ] 完成原计划三台设备的扩展挂载与真实同步验证；Linux 笔记本接入 Pi 后补测。
- [x] 按 §6.1 实现每轮基线与主机短标记注入；虚构 fixture 验证首次交互、取消/无 UI、角色修改、未审核/过期/项目记忆隔离及索引缺失降级。
- [ ] 逐机验收：各机首次交互由用户设置本机角色后，从两台 PC 的浏览器访问 pi-web 仍显示 VPS、本地 Pi 显示工作/家庭电脑角色及正确 OS；未知设备不猜测，并覆盖长会话/压缩及远程工具目标区分。

### P4：接入 Jev Gate

- 先离线跑标注集。
- 校准阈值和中文判断质量。
- 再接入 Pi `agent_settled`。
- 只写 pending，不直接 retain。

### P5：并行运行

- 新系统运行 2–4 周。
- Hindsight 只读查询，不再自动写入。
- 记录命中率、漏检、误报、冲突和维护成本。

### P6：停用 Hindsight

- 停止容器并保留数据卷。
- 观察确认无回退需求后，删除 Hindsight、PostgreSQL 和模型缓存。
- 保留迁移报告、备份和恢复文档。

## 14. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| Jev 中文判断不准 | 重要记忆漏检或噪声过多 | 先建立中文标注集；保守阈值；显式“记住”绕过普通门槛 |
| Jev API 故障 | 自动候选暂停 | 不阻塞对话；保留手动记忆命令 |
| 第三方看到会话片段 | 隐私风险 | 先 secret scan、脱敏；必要时关闭外部 Gate |
| Curator 误提炼 | 错误写入 | 必须显示 diff；用户批准；保留 Git 回滚 |
| 多机并发写入 | Git 冲突 | 单一 Curator 写入；`pull --ff-only`；冲突时停止自动化 |
| Markdown 规模增长 | recall 变慢 | 索引、标签、归档；必要时添加可重建 FTS |
| 记忆过期 | 错误提醒 | `status`、`expires`、定期维护；可变事实回到实时源 |
| 把 Hindsight 噪声整体迁移 | 新系统继续膨胀 | 逐条提炼，禁止批量搬运原始 units |
| Git 历史保留敏感信息 | 无法彻底删除 | 提交前扫描，敏感内容永不进入仓库 |

## 15. 对已有开源方案的取舍

### Aeterna Memory

<https://github.com/luome/Aeterna-Memory>

优点：支持 Markdown、显式写入、snapshot、handoff、冲突检查、secret scan、多 Agent adapter，并包含 Pi adapter。

限制：项目明确处于 Alpha Test；并发写入、迁移策略和命令细节仍可能变化。可以作为实现参考或固定版本试验底座，但不应未经验证直接成为唯一生产记忆源。

### Cross-Agent Memory

<https://github.com/VladimirGutuev/cross-agent-memory>

优点：强调 Git 中经过验证的项目知识、决策、事故和跨 Agent 交接。

限制：更偏项目级共享知识，不是完整的个人长期记忆系统。适合吸收其项目记忆和证据优先原则。

### ShareMemory

<https://github.com/ycl-2004/ShareMemory>

优点：项目本地、无数据库、支持 Claude Code 和 Codex、带锁和校验协议。

限制：更偏项目交接和协作状态，不完全覆盖个人身份、原则、偏好和知识分层。

### claude-memory-skill

<https://github.com/hanfang/claude-memory-skill>

优点：结构简单，使用 `core.md`、topic 文件和项目文件，容易理解。

限制：更偏 Claude Code，自动保存理念与本方案“正式写入受控”原则不完全一致。

## 16. 最终决策

最终采用以下组合，而不是在两个原始方案中二选一：

```text
Hindsight：只读迁移源，短期保留，最终退出
Markdown：长期记忆唯一真相源
记忆仓库：单仓双区——个人区（跨项目有效）与项目区 `projects/<项目名>/`（单项目有效）分区不分库
Git：版本、审计、跨设备同步
memark 扩展：单一扩展承载 Gate、recall 工具、curator 工具与 /memory 命令
recall 工具：按需加载，不全量注入
curator 工具：提炼、去重、生成 diff
Jev：每轮结束后的候选筛选器，不直接写入
用户：正式长期记忆的最终批准者
```

一句话概括：

> **让机器负责“发现可能值得记住的内容”，让规则负责“过滤”，让 Curator 负责“整理”，让用户决定“是否成为记忆”，让 Git 负责“证明它如何变化”。**

本方案同时记录设计与实施状态。当前已建立 Markdown/Git 记忆库并启用 memark；尚未停用或删除 Hindsight 容器与数据，Jev Gate 和基础注入也尚未启用。
